# Diagnostic RNG continuity protocol — not production

The experiment captures the existing Python random state at server startup. It compares twenty identical requests in one persistent server with two ten-request batches, restoring the actual saved state before the second server starts. The claim function and Python random sampling algorithm are unchanged; no fixed seed is imposed. Both sequences begin with the same captured state. Full HTTP responses and final RNG states must match, including candidates and samples, not merely scores.

This is only a single-position diagnostic. Before any versioned production adoption, extend the check to full paired boards with 3 normal workers and BEN, compare complete actions/probabilities/auctions/scores, validate readiness and actual server exit codes, and reject missing/corrupt state. Preserve both Python and any other process-global RNG states used in BEN. Audit startup calls that might consume randomness after restoration.

A production checkpoint must couple the accepted result and final RNG state to the board receipt; crashes before that commit must retain the pre-board state and original failure. Do not replace the checkpoint after a failed board or automatically retry. Store checksums and source/model/config identities. The original dead server RNG state was not captured and cannot be reconstructed from these diagnostics. This protocol does not claim to recover that lost state or authorize a production RNG change. Candidate1bd remains STOP.

Observed: the first ten responses matched exactly; the restarted second batch diverged at sequence positions 16, 18 and 19 (zero-based), and final Python RNG states differed. Saving process-global state alone is therefore insufficient. Ambient consumption/startup effects remain hypotheses, not proven causes. A second diagnostic isolates the claim stream by saving/restoring ambient state around each claim call; this is explicitly a diagnostic behavior change.
